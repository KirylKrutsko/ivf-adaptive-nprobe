# Гайд по проекту: адаптивный nprobe для IVF+PQ

Этот файл для того, кто будет рассказывать проект. Здесь объяснено, что мы делали, зачем, что
получилось и что каждое число значит. Точные таблицы и формулировки для отчёта лежат в
`report/results.md`, история решений в `WORKLOG.md`. Все числа ниже взяты из `results/` и совпадают
с отчётом на момент написания (16 ноября 2026).

---

## 1. Задача простыми словами

**Поиск ближайших соседей.** Есть база из миллиона векторов (например, дескрипторы изображений) и
запрос, тоже вектор. Нужно найти 10 ближайших к запросу векторов базы. Точный перебор сравнивает
запрос со всеми миллионом, это медленно. Приближённые методы (ANN) жертвуют небольшой долей
правильных ответов ради скорости.

**IVF (inverted file).** Базу заранее разбивают k-means на `nlist` ячеек (у нас 4096). Каждый
вектор лежит в ячейке своего ближайшего центроида. При поиске сначала считают расстояния от запроса
до всех 4096 центроидов (это дёшево), а потом сканируют только `nprobe` ближайших ячеек. Чем больше
nprobe, тем больше правильных соседей найдём и тем дольше ищем.

**PQ (product quantization).** Чтобы ячейки сканировались быстро, векторы хранятся сжатыми: 128
чисел превращаются в 16 байт. Расстояния по сжатым кодам считаются быстро, но приближённо.

**Recall@10.** Доля из 10 истинных соседей, которые попали в наши 10 ответов, усреднённая по всем
запросам. 0.9 значит «в среднем находим 9 из 10».

**Работа (work).** Сколько сжатых векторов мы просмотрели на один запрос. Мы считаем именно
векторы, а не ячейки, потому что ячейки разного размера (от 59 до 1292 векторов). К этому
прибавляется константа 200, см. ниже про переранжирование.

**Идея проекта.** Обычно nprobe один для всех запросов. Но запросы разные: у «лёгкого» все соседи
в одной ячейке, у «трудного» они разбросаны. Если выбирать число ячеек под каждый запрос, можно
сканировать меньше при том же recall. Proposal предлагал конкретное правило: брать все ячейки,
центроид которых не дальше чем в (1+ε) раз от ближайшего. Для лёгкого запроса ближайший центроид
сильно ближе остальных, получится 1–2 ячейки; для трудного несколько центроидов на одном
расстоянии, получится много ячеек.

**Два исследовательских вопроса (RQ1, RQ2).**
1. При одинаковом recall сканирует ли правило меньше векторов, чем фиксированный nprobe, и
   насколько?
2. Какую долю возможной экономии оно берёт? Возможную экономию показывает оракул: метод, который
   для каждого запроса заранее знает, сколько ячеек ему хватит. Это не практический метод, а
   потолок.

**Что обещал proposal.** Пять предсказаний: большинству запросов хватает 1–3 ячеек; оракул экономит
в несколько раз; правило берёт половину этого, 1.5–2×; экономия растёт с целевым recall; по времени
экономия меньше, чем по работе.

## 2. Что мы построили, и какие решения приняли по дороге

**Пайплайн.** Один набор скриптов, которые запускаются с конфигом. Данные → индекс → baseline →
оракул → правила → протокол сравнения → графики. Папка `experiments/`, по номеру на шаг.

**Протокол честного сравнения.** 10 000 запросов делятся пополам фиксированным сидом: **tune** и
**test**. Все параметры (nprobe, ε, пороги, модели) подбираются только на tune. Все числа в отчёте
измерены на test. Для каждой цели recall R ∈ {0.8, 0.9, 0.95, 0.99} берём минимальный параметр,
который достигает R на tune, и смотрим на работу на test. Экономия = работа baseline / работа
метода. Доверительные интервалы 95% считаются бутстрепом по тестовым запросам (1000 переборов).

**Пять решений, которые стоит уметь объяснить.**

- **D1. Потолок 256 ячеек.** Правило может захотеть сотни ячеек, нужен предел. Один и тот же
  потолок у правила, оракула и сетки nprobe, чтобы все выбирали из одного диапазона. Это второй
  параметр правила, о котором proposal не говорил, мы это называем честно.
- **D2. Два оракула.** Оракул из proposal даёт каждому запросу столько ячеек, сколько нужно
  именно ему для recall ≥ 0.9 (гарантия на каждый запрос). Но на оси графика средний recall, и
  гарантия каждому не самый дешёвый способ получить 0.9 в среднем. Поэтому главный оракул
  лагранжев: каждый запрос выбирает число ячеек, минимизируя «работа − λ·recall», λ перебираем.
  Он даёт истинную нижнюю границу работы при заданном среднем recall. Оракул из proposal
  показываем пунктиром. Разрыв между ними это цена гарантии на каждый запрос.
- **D3. Индекс обучен на всей базе.** Стандартный learn-набор SIFT (100k) меньше рекомендуемого
  Faiss для 4096 центроидов. Утечки нет: запросы в обучении не участвуют.
- **D4. ε на обычных расстояниях.** Faiss отдаёт квадраты, в коде порог (1+ε)². Смысл ε тот же, что
  в proposal.
- **D5. Переранжирование.** Самое важное техническое решение. С 16-байтными PQ-кодами recall@10
  упирается в 0.59, сколько ячеек ни сканируй: ошибка сжатия путает порядок соседей. Цели 0.8–0.99
  были бы недостижимы. Стандартный выход (IVFADC+R): взять 200 лучших кандидатов по PQ-расстоянию,
  посчитать для них точные расстояния и выбрать 10. После этого recall достигает 0.996, и
  оставшаяся потеря 0.3%, то есть recall почти целиком измеряет выбор ячеек. Эти 200 точных
  расстояний считаются как работа (константа) и входят во время. Мы проверили, что после
  переранжирования кривые для PQ16+200, PQ32+100 и индекса без PQ совпадают до третьего знака,
  так что выбор индекса на выводы не влияет.

**Проверки корректности.** 28 тестов. Главные: наш путь поиска с явным списком ячеек даёт
бит-в-бит те же расстояния, что обычный поиск Faiss при том же nprobe; счётчик просмотренных
векторов Faiss совпадает с нашей суммой размеров ячеек; оракул при c ячейках воспроизводит
реальный поиск с nprobe = c для каждого запроса; переранжирование внутри одной ячейки равно точному
поиску в ней.

## 3. Оракул: сколько ячеек на самом деле нужно запросу

**Как считается.** Для каждого запроса сканируем его 256 ближайших ячеек по одной, после каждой
сливаем кандидатов, переранжируем и записываем recall. Получаем для каждого запроса кривую
recall(c) и работу(c) для c от 1 до 256. Один проход на все 10k запросов, 3 минуты. Из этих
кривых считается всё: оба оракула, baseline, и любое правило, которое берёт ячейки в порядке
близости центроидов (а это все наши правила).

**Что показал на SIFT1M** (цель 0.9 для каждого запроса):

| медиана | нужна 1 ячейка | нужно ≤ 3 | нужно > 20 | не достигают за 256 |
|---|---|---|---|---|
| 13 ячеек | 3.6% | 14% | 33% | 9 из 5000 |

Предсказание «большинству хватает 1–3 ячеек» не подтвердилось. Медианному запросу нужно 13.
Соседи запроса в 128 измерениях разбросаны по многим ячейкам. Распределение широкое, поэтому
адаптивный выбор в принципе может помочь, но лёгких запросов не так много.

**Потолок экономии** (лагранжев оракул против фиксированного nprobe):

| R | 0.8 | 0.9 | 0.95 | 0.99 |
|---|---|---|---|---|
| потолок | 1.71× | 1.98× | 2.35× | 3.94× |

Не «в несколько раз» при 0.9, а 2×. Растёт с целью, потому что при высоких целях фиксированный
nprobe вынужден обслуживать самые трудные запросы, задирая nprobe всем.

## 4. Правило из proposal: не работает

**Результат.** При ε, подобранном на tune, правило достигает цели, но сканирует больше, чем
фиксированный nprobe при том же recall:

| R | 0.8 | 0.9 | 0.95 | 0.99 |
|---|---|---|---|---|
| экономия | 0.77× | 0.73× | 0.77× | 0.93× |

Меньше 1 значит хуже. При 0.9 правило тратит на 37% больше работы. Интервалы узкие, результат
надёжный. По хвосту тоже хуже: при равной работе у правила больше запросов с recall ≤ 0.5 (5.6%
против 2.5% у baseline).

**Почему.** Это надо уметь объяснить, это главный аналитический результат.
- Правило неплохо *ранжирует* запросы по трудности: корреляция Спирмена его числа ячеек с
  оракулом 0.70. Если те же числа ячеек раздать случайным запросам, становится сильно хуже.
  Значит, сигнал есть.
- Но *отображение* «скор → число ячеек» плохое. При ε для цели 0.9 среднее число ячеек 39, тогда
  как baseline хватает 26 для всех; у 1% запросов 239 ячеек. Запросы с плоским профилем расстояний
  (много центроидов примерно на одном расстоянии) получают сотни ячеек, которые почти не добавляют
  recall. Оракул делает наоборот: на безнадёжных запросах экономит.
- У правила один параметр, и он не может одновременно быть чувствительным к лёгким запросам и
  ограниченным на трудных.

## 5. Починки на тех же данных: что дают расстояния до центроидов

**Потолок на число ячеек.** min(правило(ε), cap), cap и ε подбираются вместе на tune. Даёт
1.11 / 1.13 / 1.16 / 1.16×. Единственное правило, которое выигрывает и по времени (1.03–1.09×),
потому что это один вызов сканирования плюс маска.

**Подогнанное статическое правило** (расширение 6 из proposal). Линейная регрессия от 17 признаков
из расстояний до центроидов (логарифмы отношений d_j/d_1 на 15 рангах, log d_1, средний размер 8
ближайших списков) к логарифму числа ячеек оракула. Обучение на tune, одна модель на цель, масштаб
подбирается кросс-фитом. Даёт 1.16 / 1.23 / 1.30 / 1.38× на SIFT. Корреляция с оракулом 0.72, едва
выше, чем у ratio (0.70): весь выигрыш из калибровки, а не из лучшего сигнала.

**Десять других семейств правил** (перебор на tune): абсолютный gap d_j − d_1; расстояние до
границы ячейки (до биссекторной гиперплоскости между центроидами) как порог, как порядок, и в
двухстадийном поиске; остановка по терпению. Ни одно не обгоняет baseline больше чем на 10–20%.

**Почему идея с границами не работает** (её предлагал Кирилл, это хороший вопрос на защите).
Нижняя граница расстояния до ячейки корректна (0 нарушений на 1200 проверках), но в 128
измерениях она в медиане составляет лишь 20% реального расстояния до ближайшего вектора ячейки.
Десятый сосед запроса лежит на расстоянии 226, ближайший центроид на 213, а границы соседних
ячеек на 10–70. Условие «граница ближе, чем текущий сосед» выполняется почти для всех ячеек и
ничего не отсекает. Это проклятие размерности для branch-and-bound.

## 6. Правило остановки: смотреть на ход сканирования

**Идея.** Расстояния до центроидов известны до сканирования. Но во время сканирования поиск
узнаёт больше: каково PQ-расстояние до текущего 10-го кандидата, как оно меняется, входят ли
новые кандидаты в список. Это бесплатно, PQ-расстояния всё равно считаются.

**Реализация.** Ячейки сканируются раундами (1, 2, 3, 4, 5, 6, 8, 10, …, 224, 256; 26 точек
решения). После каждого раунда для каждого ещё активного запроса считаются 9 динамических
признаков плюс 17 статических, логистическая модель даёт P(продолжать). Если P < θ, запрос
останавливается. Модель обучается на tune по меткам оракула («оракул продолжил бы дальше этой
точки»), θ подбирается на tune кросс-фитом. Точные расстояния до финального переранжирования не
используются. Одна и та же функция генерирует обучающие признаки, работает на инференсе и
измеряется по времени, расхождений между обучением и запуском быть не может.

**Результат на SIFT1M:** 1.17 / 1.25 / 1.31 / 1.34×, интервалы ±0.02, это 32–42% экономии
оракула. По хвосту: при бюджете nprobe 26 правило оставляет 0.3% запросов с recall ≤ 0.5 против
2.5% у baseline.

**Три признака из 26 достаточно.** Модель только на log d_next/d_1, log r10/d_1 и log c даёт то
же самое с точностью ±0.02 при целях до 0.95; при 0.99 остальные признаки добавляют 4–6%. Её
граница решения записывается формулой. После c ячеек продолжать, если

    d_next / d_1 < K · (r10 / d_1)^p · c^q,     SIFT1M, R = 0.9: K = 1.53, p = 0.64, q = −0.085

где d_1 расстояние до ближайшего центроида, d_next до центроида следующей ячейки, r10 PQ-расстояние
до текущего 10-го кандидата, c сколько ячеек уже просканировано. Проверено вживую на реальном
поиске: формула выбирает ровно те же ячейки, что модель, на каждом тестовом запросе, на обоих
датасетах.

**Что формула значит.** Это правило из proposal с адаптивным ε. Proposal: сканировать, пока
d_next ≤ (1+ε)·d_1 с константой ε. Данные: 1+ε должно равняться K·(r10/d_1)^p·c^q, то есть расти,
когда текущий 10-й кандидат ещё далеко относительно ближайшего центроида (значит, хорошие соседи
ещё не найдены, продолжаем), и медленно убывать с числом уже просканированных ячеек. Константа не
умеет ни того, ни другого, и это в одну строку объясняет провал исходного правила. Это, пожалуй,
самый красивый результат проекта: исходная идея была правильной по форме, неправильной по
параметризации.

**Что в признаках важно, а что нет.** Абляция Кирилла: сигнал в r10 относительно следующего
центроида плюс число ячеек. Признаки «устаканился ли top-10» ничего не добавляют.

## 7. Статическое правило против правила остановки: честное сравнение

Это обсуждалось дольше всего, и на защите надо быть точным. Когда статическое подогнанное правило
было доведено до того же протокола (одна модель на цель), оказалось:

| конфигурация | статическое | остановки |
|---|---|---|
| SIFT1M, nlist 4096 | 1.16 / 1.23 / 1.30 / **1.38** | 1.17 / 1.25 / 1.31 / 1.34 |
| Deep1M | 1.20 / 1.20 / 1.32 / 1.52 | **1.24 / 1.26 / 1.36 / 1.65** |
| SIFT1M, nlist 1024 | 1.19 / 1.18 / 1.28 / 1.39 | **1.25 / 1.22** / 1.31 / 1.40 |

Вывод: на SIFT с 4096 ячейками они равны в пределах интервалов, статическое впереди при 0.99. На
Deep1M правило остановки впереди на всех целях с неперекрывающимися интервалами, на nlist 1024
впереди при 0.8–0.9 и равно выше. В 11 из 12 клеток правило остановки не хуже. Обратная связь от
сканирования добавляет там, где длиннее хвост трудных запросов, и ничего не стоит в остальных
случаях. Оба правила берут примерно треть экономии оракула.

Как это подавать: «два откалиброванных правила достигают примерно одного и того же, около трети
возможного; правило остановки устойчивее между конфигурациями и имеет интерпретируемую формулу;
статическое дешевле по времени при 0.99». Не говорить «обратная связь видит больше, чем центроиды»
в общем виде, это верно только на Deep1M.

---

## 8. Почему остальные две трети недостижимы

Оракул знает, *какие* запросы никогда не улучшатся, и экономит на них. Правило видит лишь, как
далеко текущие кандидаты и как далеко следующие ячейки, но не содержит ли следующая ячейка
истинного соседа. Лучшая корреляция чего угодно наблюдаемого с числом ячеек оракула 0.72–0.77.
Какие ячейки содержат соседей запроса, это свойство данных вокруг запроса, а не его расстояний до
нескольких центроидов.

## 9. Время

Один поток, 5000 запросов батчем, медиана из 5, цель 0.9, перемер Кирилла на тихой машине:

| метод | работа | мс/запрос | против Faiss |
|---|---|---|---|
| обычный Faiss, nprobe 26 | 7299 | 0.141 | 1.00 |
| наш путь с явным списком ячеек | 7299 | 0.142 | 0.99 |
| те же 26 ячеек в 26 вызовов (контроль) | 7299 | 0.542 | 0.26 |
| ratio + потолок | 6438 | 0.134 | 1.05 |
| статическое подогнанное | 5924 | 0.171 | 0.83 |
| правило остановки | 5853 | 0.511 | 0.28 |

- Ratio с потолком превращает 1.13× по работе в 1.05× по времени: квантизатор и переранжирование
  не уменьшаются с числом ячеек.
- Статическое правило медленнее Faiss, потому что ему нужны расстояния до 256 центроидов (0.047 мс
  против 0.009 для 26). При 0.99 оно быстрее на 15%.
- Правило остановки в 3–4 раза медленнее. Контрольная строка объясняет почему: те же 26 ячеек,
  просканированные 26 вызовами вместо одного, стоят 0.54 мс вместо 0.14. Каждый вызов Faiss заново
  инициализирует кучи и массивы и пересекает границу Python. Логика правила стоит 0.056 мс.
  Внутри раундовой структуры правило сканирует на 25% меньше, как и говорит работа. Чтобы
  выигрыш по работе стал выигрышем по времени, нужен инкрементальный скан внутри Faiss на C++,
  публичный API этого не даёт.

Предсказание proposal «время экономится меньше, чем работа» подтверждается, для правила остановки
с большим запасом.

## 10. Расширения

**nlist 1024 (ячейки в 4 раза крупнее).** Лёгких запросов стало больше: четверть укладывается в 3
ячейки (было 14%). Но потолок оракула и выигрыш каждого правила остались в пределах нескольких
пунктов. Лёгкий запрос теперь стоит 1000 векторов вместо 250, трудным по-прежнему нужны десятки
ячеек, экономия складывается из их отношения. Абсолютная работа удвоилась: это просто худший
индекс.

**Deep1M (96 измерений, дескрипторы изображений).** Та же картина метод за методом. Хвост трудных
запросов длиннее (34 не достигают 0.9 за 256 ячеек против 9), и там правило остановки сильнее
всего: при 0.99 оракул мог бы дать 5.2×, правило даёт 1.65×, половину возможного. Единственное
место в проекте, где исходное ratio обгоняет baseline: Deep при 0.99, 1.15×, и то упираясь в
потолок у 27% запросов.

**Перенос между датасетами.** Модель с одного датасета на другом без переобучения теряет не больше
0.02 экономии, но её порог не переносится (recall 0.68 или 0.96 вместо 0.90). Одна общая модель,
обученная на tune обоих датасетов с одним порогом, даёт 0.904 на SIFT и 0.901 на Deep без потери
экономии. Для нового датасета нужно несколько сотен tune-запросов, чтобы подобрать порог, а не
новая модель. Компактная формула переносится лучше полной модели (0.93 вместо 0.68).

## 12. Как рассказать за 10–12 минут

1. **Задача и идея** (1 слайд). IVF, nprobe одинаковый для всех, а запросы разные. Правило (1+ε).
2. **Как мерили** (1 слайд). Индекс, переранжирование и почему оно нужно (потолок 0.59),
   работа = векторы + 200, tune/test, оракул как потолок. График 1 с кривыми.
3. **Сколько ячеек нужно запросу** (1 слайд). Гистограмма (график 2). Медиана 13, не 1–3. Потолок
   2× при 0.9, 4× при 0.99.

## 13. Вопросы, которые скорее всего зададут

**«Вы же обещали проверить простое правило без обучения, а сделали логистическую регрессию».**
Проверили: правило не работает, и объяснили почему. Дальше спросили, сколько вообще достижимо.
Ответ дало минимальное обучение: модель из 3 признаков и 4 чисел, никакой библиотеки, обучается за
3 секунды. Её граница решения это то же правило (1+ε) с адаптивным ε. Proposal сам указывал шаг к
Li et al. как расширение 6.

**«Почему recall после переранжирования, а не сырой?»** Сырой PQ16 упирается в 0.59 из-за ошибки
сжатия, и ни одно правило выбора ячеек на это не влияет. Переранжирование стандартно (IVFADC+R).
После него recall на 99.7% определяется выбором ячеек, что и есть предмет работы. Мы проверили, что
результат не зависит от варианта индекса.

**«Что такое оракул и почему два?»** Оракул знает кривую recall(c) каждого запроса. Пер-запросный
гарантирует recall каждому, лагранжев минимизирует среднюю работу при среднем recall. Второй это
правильная граница для метрики на оси и он левее. Разрыв между ними сам по себе результат: цена
гарантии на каждый запрос.

**«Почему правило остановки медленнее, если оно сканирует меньше?»** Из-за API Faiss: каждый раунд
это отдельный вызов, который заново инициализирует структуры. Контрольный замер: те же ячейки тем
же числом вызовов стоят в 4 раза дороже. Логика правила стоит 0.056 мс. Нужен инкрементальный скан
внутри библиотеки.

**«Насколько надёжны числа?»** Все параметры на tune, все числа на test, бутстреп-интервалы около
±0.02. Воспроизведено на втором датасете и другом nlist. Каждое правило проверено вживую через
реальный поиск, а не только по кривым.

**«Что бы вы делали дальше?»** Реализовать инкрементальный скан на C++ и измерить время честно.
Попробовать датасет с другой структурой (GloVe). Признаки, которые видят, *в какой* ячейке лежат
соседи, а не только как далеко текущие кандидаты: например, статистику плотности вокруг запроса.

**«Почему nlist 1024 не помог, хотя лёгких запросов стало больше?»** Лёгкий запрос стал стоить
1000 векторов вместо 250. Экономия это отношение между стоимостью лёгких и трудных запросов, а не
доля лёгких.

**«Потолок 256 это честно?»** Это второй параметр, мы его называем. Исходное правило упирается в
него у 28% запросов при 0.99, что само по себе симптом проблемы; правило остановки реже.

## 14. Словарь

- **ANN**: приближённый поиск ближайших соседей.
- **IVF, nlist, nprobe**: разбиение на ячейки, их число, число сканируемых ячеек.
- **PQ, IVFADC**: сжатие векторов в коды; IVF + PQ по остаткам от центроида.
- **Переранжирование (re-ranking, IVFADC+R)**: пересчёт точных расстояний для лучших кандидатов.
- **Recall@10**: доля найденных из 10 истинных соседей.
- **Работа (work, ndis)**: число просмотренных сжатых векторов плюс 200 точных расстояний.
- **Tune / test**: половины запросов для подбора параметров и для измерения.
- **Оракул**: метод, знающий кривую recall каждого запроса; лагранжев и пер-запросный.
- **Экономия (saving)**: работа baseline / работа метода при одинаковом среднем recall.
- **Захваченная доля (captured)**: (работа baseline − работа метода) / (работа baseline − работа оракула).
- **Ratio-правило**: правило (1+ε) из proposal. **Cap**: потолок на число ячеек.
- **Статическое подогнанное правило**: регрессия от расстояний до центроидов к числу ячеек оракула.
- **Правило остановки**: решение «продолжать или нет» после каждого раунда по признакам
  сканирования. **Компактная формула**: его версия из трёх признаков.
- **d_1, d_next, r10, c**: расстояние до ближайшего центроида, до следующего, PQ-расстояние до
  10-го кандидата, число просканированных ячеек.
- **Бутстреп**: переборка тестовых запросов с возвращением для оценки доверительного интервала.
- **Спирмен 0.70**: ранговая корреляция числа ячеек правила с числом ячеек оракула.
